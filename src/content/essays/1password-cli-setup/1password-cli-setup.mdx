I started using 1Password in 2015, and it has made everyday logins so much easier that I'd almost call it life-changing.

It's a password manager that keeps my passwords, two-factor authentication codes, and passkeys together. I don't have to remember a different password for every account. Most of the time, logging into a site or app takes a click, and everything syncs between my MacBook, Windows desktop, and iPhone.

I also use it to supply credentials to the [scripts that run this site](/wordpress-to-astro/).

The publication workflow runs in GitHub Actions. It needs an API key to send the newsletter through Kit and a deploy hook to request a site rebuild. The 1Password CLI loads those values from a 1Password Environment when the script runs. Nobody needs to approve a prompt on my laptop for that job to start.

I'll walk you through setting up the same approach for your own project. We'll use a small script and a dummy API key, then get it running in GitHub Actions. I'll also explain how I'd limit a coding agent's access to those credentials.

Code that receives a secret can expose it. Keeping credentials in 1Password reduces where I store them, but I still need to decide which programs and agents can use them.

## Install and Set Up 1Password CLI

The command-line interface, or CLI, lets me use 1Password from a terminal. Its command is `op`. I can use it to retrieve an item or start a script with the credentials that script needs.

Before installing it, there are a few names worth separating:

| Part | What It's For |
| --- | --- |
| Desktop app | Stores and manages my account locally and lets me approve CLI access with device authentication. |
| Vault | Holds items such as website logins, API credentials, and SSH keys. |
| Environment | Holds a set of named variables for a project or task, separately from vault items. |
| Service account | Gives automation access to selected vaults or Environments without an interactive approval prompt. |

### Install the Stable CLI

You'll need a 1Password subscription and the desktop app with your account added. Install the latest stable CLI using the [instructions for your operating system](https://www.1password.dev/cli/get-started), then open a terminal. Use PowerShell on Windows.

Check which version was installed:

```sh
op --version
```

The Environment examples later in this guide need **1Password CLI 2.41.0 or newer**, where `op run --environment` is available in the [stable release](https://www.1password.dev/environments/read-environment-variables). There is no need to install a beta for that command. If you have an older version, update it using the same package manager or installer you used to install it.

### Connect the Desktop App

In the 1Password desktop app:

1. Unlock your account.
2. Open **Settings → Developer**.
3. Turn on **Integrate with 1Password CLI**.

For authentication, enable Windows Hello in 1Password on Windows, or **Unlock using system authentication** under **Settings → Security** on Linux. Linux also needs PolKit and a running authentication agent.

<Figure src={cliIntegration} alt="1Password Settings, with Developer selected and the checked Integrate with 1Password CLI option outlined in red.">
  Enable CLI integration under Settings → Developer so the terminal can authenticate through the desktop app.
</Figure>

Now run:

```sh
op vault list
```

Approve the request in 1Password. The command should list the vaults your account can access without printing the passwords inside them.

If you have multiple accounts in the desktop app, run `op signin` to choose the intended one. You can also select an account for a single command:

```sh
op vault list --account my.1password.com
```

Replace `my.1password.com` with your account's sign-in address if it differs. The [desktop integration guide](https://www.1password.dev/cli/app-integration) covers account selection and connection errors.

The CLI now has your account's access, which can extend beyond the project open in your terminal. For unattended work, I'll use a service account with narrower permissions.

## Create a 1Password Environment

A 1Password Environment holds named variables for a project or task. I'll call ours `guide-development` and use it for the same script locally and in GitHub Actions.

### Add the Variables

In the 1Password desktop app:

1. Open **Developer** in the sidebar, then **View Environments**.
2. Select **New environment**.
3. Name it `guide-development`, check that you're using the intended account, and select **Save**.
4. Select **New variable** and add each of the following name-value pairs.
5. Select **Save** when both variables are entered.

| Name | Value |
| --- | --- |
| `APP_ENV` | `development` |
| `API_KEY` | `demo-not-a-real-key` |

The sample key cannot authenticate with any service. We'll use it to check that a script receives the variable. Leave `API_KEY` hidden by default for the output-masking example below.

<Figure src={environmentVariables} alt="Editing the guide-development Environment with APP_ENV and API_KEY, and Hide value by default selected for API_KEY.">
  Keep the API key hidden by default using its three-dot menu, then save the variables.
</Figure>

If Environments are unavailable in a managed account, ask an owner or administrator to check the [Environments policy](https://www.1password.dev/environments#turn-the-environments-policy-on-or-off).

### Copy the Environment ID

Inside the Environment, select **Manage environment → Copy environment ID**. Keep that ID handy for the next command.

The ID identifies the Environment; it does not grant access to its variables. The CLI still needs to authenticate with an account allowed to read it.

### Use Existing Project Variables

For an existing project, **Import .env file** saves entering every variable by hand. Check what the file contains before importing it, and keep development credentials separate from production credentials.

For example, `my-app-development` and `my-app-production` can have the same variable names with different values and access permissions. Reading an Environment through `op run` supplies its set of variables, so group them by what the receiving program needs.

Importing leaves the original file in place. Once the application works with 1Password, remove the plaintext copies you no longer need. If a credential has reached Git history, logs, or an agent conversation, rotate it with the service that issued it.

## Load Environment Variables With `op run`

Before connecting an application to a real service, I want to check that it can receive the variables. For this example, I'll use Node.js, which also runs this site's automation.

Install [Node.js](https://nodejs.org/) if you don't already have it, then check that it's available in your terminal:

```sh
node --version
```

Create a file called `check-env.mjs`:

```js
const requiredVariables = ["APP_ENV", "API_KEY"];
const missingVariables = requiredVariables.filter((name) => !process.env[name]);

if (missingVariables.length > 0) {
  console.error(`Missing required variables: ${missingVariables.join(", ")}`);
  process.exit(1);
}

console.log("Both required variables are available.");
```

The script checks for non-empty values and reports missing variable names without printing their values. It makes no API calls.

### Run the Script Through 1Password

From the directory containing the script, run this command, replacing `YOUR_ENVIRONMENT_ID` with the ID you copied:

```sh
op run --environment YOUR_ENVIRONMENT_ID -- node check-env.mjs
```

The first part tells 1Password which Environment to load. The `--` separates the CLI's options from the command it will start: `node check-env.mjs`.

Approve access in the desktop app if prompted. With both variables configured, the script should print:

```text
Both required variables are available.
```

1Password starts Node with the variables available through `process.env`, so the script needs no 1Password library.

For a check without 1Password, clear both variables inside a fresh Node process before loading the script:

```sh
node -e "delete process.env.APP_ENV; delete process.env.API_KEY; import('./check-env.mjs')"
```

That should report both names as missing and exit with status 1. It does not change the variables in your current shell. Running with `op run` again should pass.

### What Happens to the Values?

`op run` supplies the variables to the command it launches, rather than exporting them into the terminal session that launched it. Child processes started by that command can inherit them too. A long-running application needs to restart through `op run` to receive updated values from 1Password.

To see output masking with our **dummy Environment only**, run:

```sh
op run --environment YOUR_ENVIRONMENT_ID -- node -p "process.env.API_KEY"
```

With the variable hidden by default, the CLI conceals its value in the output. The running program still receives the actual value. Masking helps with accidental output; it does not prevent code from using or leaking a credential.

For a real application, replace `node check-env.mjs` with its startup command. I would launch only the application that needs the key. Starting an entire agent session through `op run` would also give those variables to the agent and potentially the commands it runs.

## 1Password Environments and `.env` Files

If I put an API key in a regular `.env` file, that key stays on disk between runs. Any tool with permission to read the file can retrieve it, including a coding agent inspecting my project. Adding the file to `.gitignore` helps keep it out of commits, but does nothing to restrict that access.

With `op run --environment`, I can supply that key when the application starts without keeping a readable copy in the project directory.

[dotenvx](https://dotenvx.com/docs/quickstart) addresses the same plaintext-file problem through encryption. It encrypts values inside a `.env` file, then decrypts and injects them when the application runs. The encrypted file can travel with the code, while the private key needs separate protection. If an agent can read both that file and the private key, such as one stored in `.env.keys`, it can decrypt the values too.

With dotenvx, I need to protect the decryption key. With 1Password, I need to control which accounts and processes can retrieve the secrets.

| Approach | What Stays on Disk | How the Application Gets the Values |
| --- | --- | --- |
| Plaintext `.env` | The values themselves | A dotenv loader reads the file. |
| dotenvx-encrypted `.env` | Encrypted values; the private key needs separate protection | `dotenvx run` decrypts and injects them using the private key. |
| File containing `op://` references | References to fields in vault items | `op run --env-file` resolves them and starts the application. |
| 1Password-mounted `.env` | A named pipe, not a regular file containing the values | A compatible loader reads from it after authorization. |
| `op run --environment` | No secrets file required | The CLI starts the application with the variables. |

### When Secrets Already Live in a Vault

A secret reference points to a field in an existing 1Password item. For example, this file could map a vault credential to the `API_KEY` our script expects:

```dotenv
APP_ENV=development
API_KEY="op://Development/Demo API/credential"
```

Copy the appropriate field's secret reference from your own item and use it as the `API_KEY` value. The example above assumes a vault named `Development`, an item named `Demo API`, and a field named `credential`.

Save the mapping as `.env.references`, then run:

```sh
op run --env-file=.env.references -- node check-env.mjs
```

A regular dotenv loader will not resolve `op://` references by itself. Here, the CLI retrieves the value before starting Node. Its authenticated account still needs permission to read the item.

A file containing only references and non-sensitive configuration can be versioned without including the credentials. Review it first: vault and item names may still reveal information you would rather keep private.

### When the Application Needs a File

The [local `.env` feature](https://www.1password.dev/environments/local-env-file) makes an Environment readable through a named pipe. It looks like a file path, but 1Password supplies the contents when a program reads it, rather than storing them there as plaintext.

This optional feature is supported only in 1Password for macOS and Linux. Windows users can keep using `op run --environment`.

To try it with the demo Environment:

1. Open `guide-development` in 1Password.
2. Under **Connect to**, select **Connect** beside **Local .env file**.
3. Select **Choose file path** and pick an unused path, such as `.env.1password` inside your project.
4. Select **Mount .env file**.
5. Configure your application's dotenv loader to read that path and approve access when prompted.

Our `check-env.mjs` script reads variables from `process.env`. To try a mounted file, use an application with a compatible dotenv loader from the documentation's table.

Once authorized, the mount can be read by other processes with access to it until 1Password locks or you disable it. Approval is not restricted to the first application that asked.

Mounted files also have practical limits. Simultaneous readers can interfere with each other, and tools such as Vite can repeatedly restart when watching the mount. For this walkthrough, I'll keep using `op run`: it avoids those file-reading issues and gives us the same command pattern to carry into CI.

## Give AI Agents Limited Access to Secrets

I can ask [an agent to write code](/what-is-vibe-coding-how-to-do-it/) that reads `process.env.API_KEY`, then launch the application through `op run`. The agent can work with the variable name without having the key pasted into the conversation. Our verification script lets it check whether the variable arrived without printing its value.

But an agent allowed to edit and execute that application could change it to send the key somewhere else. An instruction saying “never reveal secrets” does not remove that ability. If I need to prevent access, I need enforced restrictions on the commands, files, and credentials available to the agent.

I would give the application a development key with only the permissions it needs. The 1Password service account controls which secrets it can retrieve. The service issuing each key controls what that key can do.

### Treat Website Logins Separately

My [X cleanup script](/automated-x-account-cleanup/) ran in a browser where I was already logged in. It could act on my account without receiving a password.

For an agent signing in to a website, I would use a dedicated account with only the permissions the task needs. Its Login item can live in a separate vault accessible to a service account, rather than sharing access to my everyday accounts.

I would check how the browser tool handles credentials before giving it access. A tool that asks the model to supply a literal password has a different exposure risk from a runner that reads it internally. Passwords can appear in tool arguments, logs, or screenshots; a saved browser session can also retain access after the password is no longer in use.

Instructions hidden in a webpage or repository file can try to persuade an agent to expose credentials. This is a form of prompt injection. Limiting the secrets and tools available to the agent reduces what a successful attack could reach.

## Use 1Password With GitHub Actions

Next, we'll run `check-env.mjs` on GitHub's servers through a manually triggered workflow. It will read the demo Environment and report whether both variables arrived.

### Create the Service Account for GitHub

GitHub's runner needs a service-account token so it can authenticate without waiting for me to approve a request in the desktop app.

In the [1Password service-account wizard](https://start.1password.com/developer-tools/infrastructure-secrets/serviceaccount/):

1. Name the account `guide-github-actions`.
2. Leave vault creation disabled and grant no vault access.
3. Select only the `guide-development` Environment.
4. Create the account and save its token in 1Password immediately.

That account can read the demo variables, but it cannot edit them. The token is shown only once. Keep it out of the workflow file and any screenshots.

<Figure src={serviceAccountAccess} alt="1Password service-account setup with guide-development selected for Read access and other visible Environments marked No Access.">
  Select guide-development and leave unrelated Environments unchecked.
</Figure>

### Add Two GitHub Settings

Open the GitHub repository where you want to run the example, then go to **Settings → Secrets and variables → Actions**. You need permission to manage that repository's Actions settings.

Add these two entries in their respective tabs:

| Tab | Button | Name | Value |
| --- | --- | --- | --- |
| Secrets | New repository secret | `OP_SERVICE_ACCOUNT_TOKEN` | The token from the service account you just created. |
| Variables | New repository variable | `OP_ENVIRONMENT_ID` | The ID copied from `guide-development`, not its name. |

The token belongs in **Secrets** because it grants access. The Environment ID only identifies what to load, so it can go in **Variables**. This example uses repository settings; there is no separate GitHub Environment to configure.

Leave `API_KEY` and `APP_ENV` in 1Password.

<Figure src={githubActionsSecrets} alt="GitHub Actions Secrets tab listing OP_SERVICE_ACCOUNT_TOKEN under Repository secrets, with the Variables tab beside it.">
  Save OP_SERVICE_ACCOUNT_TOKEN under Secrets, as shown here. Switch to Variables to add OP_ENVIRONMENT_ID.
</Figure>

### Add the Workflow File

Put the earlier `check-env.mjs` script at the root of the repository. It uses only Node's built-in features, so this example needs no package installation.

Create `.github/workflows/check-1password.yml` with:

```yaml
name: Check 1Password access

on:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false

      - uses: actions/setup-node@v7
        with:
          node-version: 24
          package-manager-cache: false

      - uses: 1password/install-cli-action@v4
        with:
          version: latest

      - name: Check variables from 1Password
        env:
          OP_SERVICE_ACCOUNT_TOKEN: ${{ secrets.OP_SERVICE_ACCOUNT_TOKEN }}
          OP_ENVIRONMENT_ID: ${{ vars.OP_ENVIRONMENT_ID }}
        run: |
          op run --environment "$OP_ENVIRONMENT_ID" -- \
            env -u OP_SERVICE_ACCOUNT_TOKEN node check-env.mjs
```

GitHub supplies the service-account token only to the final step. The CLI uses it to read the Environment, then starts our script with its variables. `env -u OP_SERVICE_ACCOUNT_TOKEN` removes the token from the script's inherited environment; the script needs the application variables, not the credential used to retrieve them.

The installer selects the latest stable CLI rather than a beta.

### Run It and Check the Result

Commit both files and get them onto the repository's default branch, usually `main`. GitHub requires the workflow to be there before it can be [triggered manually](https://docs.github.com/en/actions/managing-workflow-runs/manually-running-a-workflow).

Then:

1. Open the repository's **Actions** tab.
2. Select **Check 1Password access**.
3. Select **Run workflow**, choose the default branch, and confirm.
4. Open the run, then the `check` job and **Check variables from 1Password** step.

The expected script output is:

```text
Both required variables are available.
```

A successful run checks that the runner can authenticate, read the selected Environment, and pass both variables to Node. To check whether a real API key works, the script would need to call that service.

If the run fails, check these first:

- **Authentication failure:** confirm the token is saved under the exact secret name and the service account is still active.
- **Environment access failure:** confirm the ID belongs to `guide-development` and that the service account was granted access to it.
- **Missing required variables:** check the names `APP_ENV` and `API_KEY`, their non-empty values, and that you saved your edits in 1Password.

If there is no **Run workflow** button, check that the workflow file is on the default branch and includes `workflow_dispatch`. Repository or organization policy must also allow the actions used in the example.

### Replace the Check With Your Actual Job

In this site's workflow, the command after `env -u OP_SERVICE_ACCOUNT_TOKEN` is `pnpm run publication` instead of `node check-env.mjs`. Its earlier steps install the project's dependencies. The script receives its Kit API key and Cloudflare deploy hook through the same mechanism we just configured.

For your project, replace the check with the command that needs the credentials and add its installation steps before it. Keep the token attached to that step rather than the whole job. Review the code that will run with those secrets; do not extend this example to execute untrusted pull-request code with credentials.

GitHub Secrets alone is also a valid way to store CI credentials. Using 1Password keeps the application values in the same place I manage them for other workflows. It still leaves one credential in GitHub: the service-account token.

If I replace this site's Kit API key, I update `KIT_API_KEY` in the 1Password Environment. The next publication run gets the replacement without a change to the workflow file. If I rotate the 1Password service-account token instead, I update `OP_SERVICE_ACCOUNT_TOKEN` in GitHub's repository secrets.

If the service-account token leaks, I need to [revoke it in 1Password](https://www.1password.dev/service-accounts/manage-service-accounts#revoke-a-service-account-token). Deleting the repository secret would not invalidate a stolen copy. And if someone already used it to retrieve the Kit key, that key needs replacing in Kit too.

## For the Next Automation

For another small automation, I'd start with an Environment containing only the variables it needs. Then I'd choose whether to approve access myself or give it a service account of its own.
